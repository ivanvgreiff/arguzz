# Cursor Ignore Configuration

This document describes **exactly** what Cursor ignores in this repository, why,
and how an ignored file appears to the AI agent (Opus). The goal is to keep
Cursor fast on a ~21 GB / ~57k-file repo while keeping all real source code (and
most text) readable by the agent.

There are **three** mechanisms, each with different effects:

| File | Effect on indexing | Effect on Opus reading | Effect on watcher/search |
| --- | --- | --- | --- |
| `.cursorignore` | Removed from index | **Blocked** — Opus cannot read via its file tools | n/a |
| `.cursorindexingignore` | Removed from index | Still **readable** on request | n/a |
| `.vscode/settings.json` | n/a | No effect (still readable) | Excluded from watcher/search/Pylance |

> Cursor also automatically skips anything matched by `.gitignore` for
> **indexing** (but `.gitignore` does **not** block Opus reads and does **not**
> exclude from the file watcher).

After the current configuration, the file watcher tracks ~6,787 files (down from
~29,744 before `target/` dirs were excluded, and ~57,000 unmanaged).

---

## 1. `.cursorignore` — de-indexed AND blocked from Opus

Binary build output, archives, and raw generated dumps that Opus cannot
meaningfully read. Opening them via the agent's file tools is blocked.

| Pattern | What it matches | Notes |
| --- | --- | --- |
| `**/target/` | **All Cargo build dirs** (thesis + workspace) | ~7.8 GB / ~23k files in workspace alone; 285 MB `.rlib`, 226 MB `.rmeta`, 97 MB host binaries, thousands of deps |
| `thesis_side_experiments/*/artifacts/` | Generated experiment artifacts | ~13k raw `.json`/`.gz`/`.log` files |
| `thesis_side_experiments/*/frozen_host/` | Frozen host binaries | ~97 MB ELF binaries |
| `thesis_side_experiments/**/*.db` | SQLite DBs **inside thesis only** | All other `.db` files stay readable |
| `bundles/` | Archive tarballs | 15 `.tar.gz` files, ~1.5 GB |
| `pos-examples/` | Reference clone | Not part of arguzz |

### Why `target/` is safe to fully block

`target/` contains **only compiled output** — `.rlib`, `.rmeta`, object files,
and linked binaries. None of it is hand-written or LLM-readable, and it is
regenerated by `cargo build`. Critically, **every hand-edited source file lives
OUTSIDE `target/`** (see Section 4), so blocking `target/` loses nothing
editable. `workspace/output/` for example is 3.2 GB of which 3.2 GB is `target/`
and only **11 small files** (~176 KB) are actual source.

### Explicitly NOT in `.cursorignore` (readable + indexed)

- All `workspace/` **source** (everything outside `target/`) — see Section 4.
- All root-level `*.db` files (e.g. `a4_coverage.db`, `bandit_*.db`).
- All `a4/**/*.db` files (262 of them).
- Every `.py` / `.rs` / `.cpp` / `.h` / `.md` / `.toml` / `.sh` source file
  anywhere, including the harness/dispatch scripts inside
  `thesis_side_experiments/` (outside `artifacts/`, `target/`, `frozen_host/`).

## 2. `.cursorindexingignore` — de-indexed but STILL readable by Opus

Removed from the search index for speed, but Opus can still open them on
request. Applies repo-wide, **including `a4/`**.

| Pattern | What it matches |
| --- | --- |
| `*.log` | All log files (incl. the 86 MB audit logs in `a4/audits/`) |
| `*.stdout` | Captured stdout dumps |
| `*.stderr` | Captured stderr dumps |
| `*_output.txt` | Captured run-output text files |

---

## 3. `.vscode/settings.json` — watcher / search / Pylance excludes

Performance only. Does **not** block Opus reads. Excludes from the OS file
watcher, the search panel, and the Python language server:

- Universal caches: `**/.git`, `**/.venv`, `**/__pycache__`, `**/.mypy_cache`,
  `**/.pytest_cache`, `**/.ruff_cache`, `**/node_modules`
- `**/target/` (all Cargo build dirs)
- `thesis_side_experiments/*/artifacts/`
- `thesis_side_experiments/*/frozen_host/`
- `bundles/`
- `pos-examples/`

Also sets `python.analysis.diagnosticMode: openFilesOnly` so Pylance analyzes
only open files instead of scanning the whole tree.

`workspace/` source (outside `target/`) and all of `a4/` remain fully watched,
searched, and analyzed.

## 5. How an ignored file appears to the LLM (Opus)

Short answer: **Opus can tell the file exists, and gets a clear "ignored"
signal — it does not look like a missing file or a random error.** But behavior
differs by mechanism:

### `.cursorignore` (blocked)
- The path **still shows up** in the file tree, in `ls`/`find` output, and in
  glob results — so the agent knows the file is there.
- If the agent tries to read it with its file-read tool or `@`-mention it, the
  attempt is **refused with an explicit "ignored by .cursorignore" style
  message** — distinguishable from "file not found" or a tool error.
- It is **not surfaced by semantic/codebase search**, so the agent will not
  *proactively* discover its contents; it only knows it exists if it lists the
  directory or you mention it.
- To let the agent actually use it, do one of:
  1. Temporarily remove/comment the matching line in `.cursorignore` (best for a
     one-off), then reload the window.
  2. Move the pattern to `.cursorindexingignore` instead (readable, just not
     indexed).
  3. Paste the relevant snippet directly into chat.
- Note: a terminal command run by the agent (e.g. `cat`) may still print the
  file depending on Cursor's terminal-enforcement setting, but the **reliable,
  supported** way to grant access is to un-ignore it.

### `.cursorindexingignore` (de-indexed, readable)
- Fully readable on request. The only difference vs a normal file is it won't
  appear in semantic search results, so you may need to point the agent at the
  exact path.

### `.vscode/settings.json` excludes
- No effect on the agent's ability to read. These files just don't trigger the
  watcher and don't appear in the search panel / Pylance.

> Practical rule: if you ever need the LLM to read something currently under
> `.cursorignore` (e.g. inspect a specific build artifact or a thesis `.db`),
> temporarily un-ignore that one path and reload — don't assume an error means
> something is broken. This document is the source of truth for what is
> intentionally blocked vs. genuinely missing.
