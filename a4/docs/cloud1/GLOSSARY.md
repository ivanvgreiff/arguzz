## RISC-V / RISC Zero trace concepts

| Term | Definition |
|---|---|
| **guest** | The RISC-V program being executed and proved. For our current campaign it's `c0c1_differential_guest` (a two-circuit equivalence-check program generated by arguzz's CircIL framework; source at `workspace/output/methods/guest/src/main.rs`). |
| **host** | The Rust program that drives the guest's execution and proving. `risc0-host` is our patched host binary; it embeds the guest ELF and runs the zkVM. |
| **step** (a.k.a. **user_cycle**) | One iteration of the user-program in the ZK virtual machine. Roughly: one RISC-V instruction. The first step is `step=0` (boot/setup); the last is `step=total_steps-1`. |
| **cycle** (a.k.a. **circuit cycle**) | A micro-operation within the ZK circuit. Most RISC-V instructions are 1 cycle, but some (POSEIDON, MUL multi-pass, step 0 setup, ECALL) span multiple cycles. So **multiple cycles can have the same step**. |
| **cycle_idx** | Index into the trace's `cycles[]` array (0-based, monotonically increasing). |
| **major** | The "instruction-class column" of the ZK circuit at a cycle. Integer 0..12. Determines which circuit table the cycle is verified against. Values for our codebase: |
| | • `0/1/2` = MISC0/1/2 (RV32IM ALU: Add, Sub, Xor, Or, And, Slt, SltU, AddI, XorI, OrI, AndI, SltI, SltIU, Beq, Bne, Blt, Bge, BltU, BgeU, Jal, JalR, Lui, Auipc) |
| | • `3` = MUL0 (Sll, SllI, Mul, MulH, MulHSU, MulHU) |
| | • `4` = DIV0 (Srl, Sra, SrlI, SraI, Div, DivU, Rem, RemU) |
| | • `5` = MEM0 (loads: Lb, Lh, Lw, LbU, LhU) |
| | • `6` = MEM1 (stores: Sb, Sh, Sw) |
| | • `7` = CONTROL0 (Eany ECALL setup, Mret) — **also catches some branch resolution**; needs E1 to disambiguate |
| | • `8` = ECALL0 (the actual ECALL syscall cycle — boundary) |
| | • `9/10` = POSEIDON0/POSEIDON1 (Poseidon hash accelerator setup) |
| | • `11` = SHA0 (SHA accelerator) |
| | • `12` = BIGINT0 (BigInt accelerator) |
| | (Authoritative source: `a4/core/inspection_data.py::summary()` lines 224-228.) |
| **minor** | Sub-classification within a major. For example: major=0, minor=0 is `Add`; major=0, minor=7 is `AddI`. Full table in `a4/core/insn_decode.py::INSN_KIND_NAMES` (kind = major*8 + minor). |
| **pc** | RISC-V Program Counter at this cycle. The next PC after the instruction (RISC0's convention; the PC of the instruction itself is `pc - 4`). |
| **txn** | "Transaction" — a memory or register read/write recorded by the circuit. Each step has 0 or more txns. |
| **txn_idx** | Index into the trace's `all_txns[]` array. |
| **txn_type** | `"reg"` (register access) or `"mem"` (memory access). |
| **addr** | Word-address of a txn. For registers, this is the word-address of the `x0..x31` register file in memory (RISC0 maps registers to a memory region). |
| **word** | The 32-bit value of a txn. For a write txn, this is the value being written. For a read txn, this is the value being read. |
| **cycle (field on txn)** | The cycle index where this txn occurs. |
| **prev_cycle (field on txn)** | The cycle index of the PREVIOUS access to the same addr (used for the memory consistency checks). |

| Region | Range | Notes |
|---|---|---|

| User code & data | `0x00040400` .. `0x0BFFFFFF` | the guest's `.text`, `.rodata`, stack, heap |
| Reserved / inter-region gap | `0x0C000000` .. `0x3FFFFFFF` | |

| Various special / I/O regions | `0x40000000` .. `0xBFFFFFFF` | not all addresses here are valid txn targets |
| Kernel / reserved | `0xC0000000` .. `0xFFFEFFFF` | |

| trampoline / special | `0xFFFF0080` .. `0xFFFFFFFF` | |

**D42 non-deterministic addresses** (Audit A1's allow-list): 188 specific addresses around `0x42000000+` (HOST_ECALL_ADDR region) and `0x000884e6+` (guest journal buffer), only at steps 170 and 3929. Their `word` field varies across host runs because those bytes are host-controlled. MEM_VAL_MOD must not target these.

### User vs kernel PC ranges (for D54 HYBRID zone classifier)

The zone classifier discriminates "user code" from "kernel code" purely by the PC range of a step's primary Decode cycle. The canonical ranges are:

| Region | Range | Used in our guest? |
|---|---|---|
| **USER** | `0x00200000 .. 0x00400000` | YES — c0c1_differential_guest's `.text` lives in this range (verified by `audit_output/E7_kernel_contamination_survey.json`) |
| **KERNEL** | `0xC0000000 .. 0xC1000000` | YES — risc0's kernel/trap-handler code; entered on ECALL, MRET cycles, boot Decode |

**Empirical breakdown (c0c1_differential_guest, --in1 5 --in4 10):**
- 90.4% of steps have user-PC Decode cycle (3516 / 3891)
- 9.6% of steps have kernel-PC Decode cycle (375 / 3891)
- 0% in "other" PC ranges (mixed user/kernel boundaries are caught by pre_ecall/post_ecall first)

Most contaminated zones BEFORE D54 (i.e. zones where many steps are actually kernel code):

| Zone | Kernel % | Sample kernel step | Implication |
|---|---:|---|---|
| step0 | 100% | step=0 pc=0xc0000004 (kernel boot) | step0 stays as singleton (precedence) |
| pre_ecall | 100% | ECALL cycle is kernel-PC by design (D13) | pre_ecall keeps kernel cycles |
| post_ecall | 56% | step=171 pc=0xc0000158 (trap handler) | D53 redefines to first user-PC return |
| core_mul | 34% | (varies) | kernel MUL ops go to kernel_other under D54 |
| core_memory_load | 14% | (varies) | kernel loads go to kernel_other under D54 |
| core_branch | (high) | kernel MRET at major=7 | kernel branches go to kernel_other under D54 |

## Zone classifier (semantic zones)

| Term | Definition |
|---|---|
| **SEMANTIC_ZONES** | The 17 zone names defined in `a4/standalone/semantic_zones.py`. Every step is assigned to exactly one zone. |
| **e** | Used in zone definitions as shorthand for "the step containing an ECALL cycle" (a cycle with `major == 8`). |
| **pre_ecall** | A zone containing the ECALL cycle itself (we put the ECALL cycle into pre_ecall by Decision D13 because ECALL setup constraints fire AT the ECALL cycle). Note: the ECALL cycle's PC is in the KERNEL range (~`0xc0000148`); pre_ecall is intentionally "kernel-flavored" by definition. See D51 for the post-D40 clarification (some pre_ecall steps are dropped as multi-cycle ambiguous; the remaining steps contain a single Decode-state cycle). |
| **post_ecall** | **(REDEFINED in D53)** The smallest `k ∈ [1, 5]` such that step `e + k` has a Decode cycle at USER PC. Originally Pro spec'd this as "e+1 only"; empirical investigation (`audit_output/E6_post_ecall_window_evidence.json`) found that e+1 is kernel-PC trap handler in 46% of cases and the user-side return point varies between e+1 and e+4. Under D54 (HYBRID), intermediate kernel-handler steps fall into `kernel_other` automatically, so post_ecall cleanly captures only the user-side return. |
| **step0** | The special singleton zone for `step == 0` (boot/setup; spans many cycles for POSEIDON init). Note: under D54 (HYBRID), the step 0 Decode cycle is at kernel PC (`0xc0000004`) but step 0 retains the `step0` singleton classification because the singleton precedence rule fires first. |
| **last_step** | The singleton zone for `step == total_steps - 1` (termination cycle). |
| **core_arithmetic** | Steps whose primary cycle has major ∈ {0, 1, 2} (RV32IM ALU) AND user-PC (after D54). |
| **core_mul** | major ∈ {3} (MUL) AND user-PC (after D54). Note: ~34% of major=3 steps in our baseline are at kernel PC and will reclassify under D54 to `kernel_other`. |
| **core_div** | **(REDEFINED in D50)** major == 4 with minor ∈ {4, 5, 6, 7} (DIV/DIVU/REM/REMU only — divides). |
| **core_shr** | **(NEW in D50)** major == 4 with minor ∈ {0, 1, 2, 3} (SRL/SRA/SRLI/SRAI — shift-rights). Split from core_div because DIV0 conflates divide and shift-right ops in one circuit table. |
| **core_memory_load** | major ∈ {5}. |
| **core_memory_store** | major ∈ {6}. |
| **core_branch** | major == 7 (CONTROL0 — includes branches, JAL, JALR, MRET). Under D54 (HYBRID), kernel-PC major=7 steps (e.g. kernel MRET) reclassify to `kernel_other`; `core_branch` becomes implicitly user-only. D48 (separate core_branch_user/core_branch_kernel split) was SUPERSEDED by D54. |
| **core_sha** | major ∈ {11}. Empty for our current guest. |
| **core_poseidon** | major ∈ {9, 10}. Empty (POSEIDON cycles exist only in step 0, which is captured by step0 singleton). |
| **core_other** | major ∈ {8, 12} not captured by ECALL-boundary rules. Empty for our current guest. |
| **kernel_other** | **(NEW in D54 — HYBRID kernel-zone)** Any step whose primary Decode cycle has PC in the kernel range (`0xC0000000..0xC1000000`) AND is NOT already classified as `pre_ecall` / `post_ecall` / `step0` / `last_step` by higher-precedence rules. One zone collecting all kernel execution into a single fat per-kind arm. See `audit_output/E7_kernel_contamination_survey.json` for the empirical motivation. Estimated 357 steps in baseline c0c1_differential_guest. |
| **pre_mret / post_mret / pre_halt / post_halt** | NOT YET IMPLEMENTED — see D14 + Q8. Empty for now. |

## Mutation kinds

| Kind | What it mutates | Valid majors | Mechanism |
|---|---|---|---|
| `COMP_OUT_MOD` | The destination-register WRITE value of a compute instruction | {0, 1, 2, 3, 4} | rewrites the txn's `word` field with a new value |
| `LOAD_VAL_MOD` | The value loaded from memory and written to the destination register | {5} | rewrites the load's destination-write txn's `word` |
| `STORE_OUT_MOD` | The value written to memory by a store instruction | {6} | rewrites the store txn's `word` |
| `PRE_EXEC_REG_MOD` | A register READ value before the instruction executes | {0..6} (where a pre-exec read exists) | rewrites the pre-execution read txn's `word` |
| `INSTR_TYPE_MOD` | The `(major, minor)` of an instruction cycle, leaving txns intact | {0..6} | rewrites `cycle.major` and `cycle.minor` |
| `MEM_VAL_MOD` | Any memory transaction's `word` value at a step (not restricted to load/store; e.g., RAM consistency txns at any step) | any step with mem txns | rewrites the mem txn's `word` |
| `INSTR_WORD_MOD_FULL` | The full 32-bit instruction fetch word at PC | {0..6} ∪ {8} | rewrites the fetch txn's `word` to a different RISC-V instruction encoding |
| `INSTR_WORD_MOD_SUR` | Surgical: only a specific bitfield (immediate, funct3, etc.) within the instruction word | {0..6} ∪ {8} | rewrites only specific bits |

## Bandit terms

| Term | Definition |
|---|---|
| **arm** | A `(mutation_kind, semantic_zone)` pair for V5, or just `mutation_kind` for V2-V4. The unit of bandit decision-making. |
| **arm_id** | String key for DB/logging. V5: `"COMP_OUT_MOD\|core_arithmetic"`. V2-V4: `"COMP_OUT_MOD"`. |
| **pull** | One mutation cycle where the bandit selected this arm. |
| **mode** | How the bandit selected the arm THIS pull: |
| | • `cold` — round-robin until each arm has `cold_start_pulls_per_arm` pulls (3 default) |
| | • `singleton` — a forced-floor pull on a singleton-zone arm (`step0`/`last_step`) until 5 pulls |
| | • `floor` — an epoch-level coverage-floor pull (55% of pulls reserved across all arms) |
| | • `adaptive` — Beta Thompson Sampling: argmax of `θ_a ~ Beta(α_a, β_a)` |
| | • `ucb` — UCB1 (V2/V3 only) |
| **success** | A Bernoulli signal: 1 if the mutation's reward exceeded a threshold; 0 otherwise. Updates the arm's Beta posterior. |
| **α / β (alpha / beta)** | Parameters of the arm's Beta posterior: `α = prior_α + successes`, `β = prior_β + (pulls - successes)`. Mean reward estimate = `α / (α + β)`. |
| **epoch** | A window of 100 mutations (`epoch_size = 100`) for the coverage-floor accounting. |
| **coverage_floor_fraction** | `0.55` — fraction of pulls per epoch that are reserved for the floor (lowest-pulls arms get priority). |
| **singleton arm** | An arm whose zone is `step0` or `last_step` (1-step zones). Pro §7.A says these need guaranteed minimum pulls. |
| **boundary arm** | An arm whose zone is a BOUNDARY_ZONE (step0/last_step/pre_ecall/post_ecall/pre_mret/post_mret/pre_halt/post_halt). |

## Cycle terminology recap (Phase 7d Inc 1 addition)

This section pins down the often-confusing relationship between trace cycles, RISC-V instructions, and the txn.cycle field. Use this when reading Audit B1, B2, B4, E5 outputs.

### Three distinct "cycle"-like quantities

| Quantity | Definition | In our code | Examples |
|---|---|---|---|
| **`user_cycle`** (a.k.a. **`step`**) | Sequential index that increments only when an RV32IM instruction *retires*. | `A4CycleInfo.step` field. | step=0,1,2,...,3929 (for our baseline) |
| **`cycle_idx`** | Index into the trace's `cycles[]` array. Every micro-operation in the ZK circuit gets one. | `A4CycleInfo.cycle_idx` field. | Up to ~32768 for our baseline |
| **`txn.cycle`** | A doubled cycle index for memory consistency. Reads = `2×cycle_idx`, writes = `2×cycle_idx + 1`. | Computed internally in Rust; we never use this directly in Python. | If `cycle_idx=16777`: read txn.cycle=33554, write txn.cycle=33555 |

**Key invariant:** `user_cycle` is **not** the same as `cycle_idx`. One `user_cycle` value (step) can span many `cycle_idx` entries — this is the source of multi-cycle ambiguity that motivated P3 / D40.

### When does `user_cycle` increment?

Only inside `preflight.rs::on_insn_end` after a "Decode" state (CycleState `state=48`). Other micro-ops do NOT increment `user_cycle`:

- Boot Poseidon initialization (state ≠ 48) — runs many cycles, all with `step=0`
- SHA-256 accelerator rounds — multi-cycle, share the user_cycle of the SHA call
- BigInt accelerator — same pattern
- ECALL handler micro-cycles — share user_cycle of the ECALL syscall
- Control flow micro-cycles — share user_cycle of the next instruction

In our code we do NOT track CycleState (`state=48` vs others) directly — but we discriminate via `cycle.major`:

| Cycle source | `cycle.major` value |
|---|---|
| User RV32IM instructions (Decode state) | 0..6 (ALU/MUL/DIV/MEM/CONTROL) |
| ECALL syscall cycle | 8 (ECALL0) |
| Poseidon accelerator | 9, 10 (POSEIDON0, POSEIDON1) |
| SHA accelerator | 11 (SHA0) |
| BigInt accelerator | 12 (BIGINT0) |

So `major ∈ {0..7, 8}` are conceptually "Decode-state" cycles (where user-meaningful work happens), and `major ∈ {9..12}` are accelerator micro-cycles that share their parent user_cycle.

### How many cycles share each step? (c0c1_differential_guest baseline)

Direct measurement on the baseline trace (3930 steps, 32768 cycles):

| Cycles-per-step | # of steps | What's happening |
|---|---|---|
| 1 | 3896 | Normal user instruction — 1 Decode cycle, no accelerators |
| 3 | 3 | Steps containing small multi-cycle ops (e.g. some MUL paths) |
| 4 | 25 | Steps with ECALL or branch resolution + adjacent micro-ops |
| 75 | 4 | Steps with mid-program Poseidon accelerator calls |
| 11889 | 1 | The boot step (step=0) — Poseidon init for the seal |
| 16574 | 1 | The terminator step (step=3929) — Poseidon finalize + cleanup |

The first column is what defines P3's "multi-cycle" question. But P3 only counts cycles **matching the kind's major filter**, so accelerator cycles never inflate the count for RV32IM kinds (see §P3 impact below).

### `txn.cycle = 2 × cycle_idx + {0,1}`

The ZK circuit splits each cycle into two phases for memory consistency:
- **Phase 0 (even txn.cycle):** reads
- **Phase 1 (odd txn.cycle):** writes

The Rust check `if txn.cycle / 2 != ctx.cycle { error }` enforces this. **We never compute this in Python**; we always work with `cycle_idx` and `txn_idx` directly.

### `prev_cycle` on a txn

For each txn, `prev_cycle` = the txn.cycle value of the PREVIOUS access to the same address. This is what the ZK circuit's memory-consistency proof uses. For our audits we generally don't need `prev_cycle` — it's just metadata for the Rust prover.

### P3 / D40 impact (empirical, measured on baseline)

How many steps per kind P3 actually drops:

| Kind | Filter | Steps with ≥1 matching cycle | Steps with >1 matching (dropped) | % dropped |
|---|---|---:|---:|---:|
| COMP_OUT_MOD | major ∈ {0,1,2,3,4} | 2615 | 0 | 0.0% |
| LOAD_VAL_MOD | major == 5 | 680 | 0 | 0.0% |
| STORE_OUT_MOD | major == 6 | 596 | 0 | 0.0% |
| PRE_EXEC_REG_MOD | major ≤ 6 | 3891 | 0 | 0.0% |
| INSTR_TYPE_MOD | major ≤ 6 | 3891 | 0 | 0.0% |
| INSTR_WORD_MOD_FULL/SUR | major ≤ 6 OR major == 8 | 3906 | 33 | 0.8% |
| MEM_VAL_MOD | (exempt — see §MEM_VAL_MOD below) | — | — | — |

So for 5 of the 7 RV32IM kind groups, P3's multi-cycle filter doesn't drop ANY steps in our baseline — the major filter already discriminates well enough. Only INSTR_WORD_MOD_* loses anything (0.8% of matching steps), concentrated at ECALL boundary steps where major=8 and the next instruction's major≤6 cycle share the same step.

### MEM_VAL_MOD's special case

MEM_VAL_MOD targets a specific `(step, txn_idx)`, not `(step, cycle)`. The txn_idx is globally unique across the trace, so the Rust hook unambiguously identifies the target regardless of how many cycles the step contains. P3's multi-cycle filter therefore doesn't apply to MEM_VAL_MOD.

### Accelerator-targeted mutations (Phase 11 deferred work)

For our current 7 kinds, `cycle.major ∈ {9,10,11,12}` (POSEIDON0/1, SHA0, BIGINT0) is correctly filtered out — none of these mutations semantically apply to accelerator cycles. This means accelerator coverage relies entirely on MEM_VAL_MOD (which is unfiltered and DOES reach accelerator memory I/O).

To target accelerators DIRECTLY (e.g. mutating a SHA input block before the SHA accelerator processes it), we'd need new mutation kinds: `SHA_INPUT_MOD`, `POSEIDON_INPUT_MOD`, `BIGINT_OPERAND_MOD`. These are deferred to **Phase 11** (post-Phase 9, post-Pro R2). See `CLOUD1_STATUS.md` row 11 and `phases/PHASE_7D_ARCHITECTURE_AUDIT.md §7` for full rationale.

## Variable-naming convention in per-arm evidence files

When you see `audit_output/per_arm_evidence/<kind>_<zone>_step<N>.md`, the structure is:

```
arm = (kind, zone)
step = step number in trace
cycle_idx = trace.cycles[] index of the cycle this step targets
selected_by = which mode picked this (cold/singleton/floor/adaptive/ucb)

BANDIT CLAIMED:
  arm_id: COMP_OUT_MOD|core_arithmetic
  zone semantic: "step where the cycle's instruction is an ALU op (major ∈ {0,1,2})"
  expected major-set: {0, 1, 2}

ACTUAL TRACE OBSERVED:
  cycle.major: 0 (= MISC0; ALU op like Add/Sub/Xor; from cycle.major @ cycle_idx=187)
  cycle.minor: 0 (= Add)
  cycle.pc: 0x4000a2bc
  step's other cycles: [cycle_idx=186 major=0 minor=7 (AddI)]

DECODED INSTRUCTION (from fetch txn):
  raw word: 0x00a50533
  decoded: "add a0, a0, a0" (RV32IM Add)
  decoded major/minor: 0/0
  ✓ MATCHES cycle.major/minor

MUTATION APPLIED:
  config: {kind: COMP_OUT_MOD, step: 42, txn_idx: 42, word: 0xDEADBEEF}
  hook stdout: <a4_comp_out_mod>{step:42, txn_idx:42, old_word:0x12345678, new_word:0xDEADBEEF, ...}
  ✓ hook landed on the cycle the universe identified
  ✓ hook.old_word matches baseline trace's txn.word for this txn_idx

OUTCOME:
  exit_code: 0
  proof_verify_failed: True
  failures: [inst_misc0.zir:42 "VerifyMulF1Witness", ...]
  reward_v2: 0.34 (L_new=2, F_new=1, G_new=0, S_new=1)

LABEL VERDICT: ✓ SEMANTIC LABEL CORRECT
  Justification: the mutation was at a step containing a real ALU op (Add); the
  arm's semantic claim "core_arithmetic" matches the actual instruction class;
  the mutation rewrote the destination register WRITE (which is what
  COMP_OUT_MOD claims to do); the resulting failures include `inst_misc0`
  (ALU-instruction integrity), consistent with the claim.
```

A LABEL INCORRECT verdict looks the same but with explicit divergence at one of the steps.
